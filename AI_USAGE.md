# How AI was used on this project

`protein.md` Chapter III asks for this explicitly: *"Be transparent about how AI
was used in your projects, and clearly identify what was generated by AI tools."*
It also sets the bar — *"I had AI generate the entire architecture… when I'm asked
to explain design decisions during the peer review, I cannot"* is the failure mode
to avoid. So this file says what we used it for, and what we did about the parts
it is bad at.

## Where AI was used

- **Boilerplate and scaffolding.** Screen skeletons, StyleSheet blocks, the Fastify
  route shells, test file structure. Reviewed line by line, then edited.
- **Unit tests.** Substantially AI-assisted, then read and adjusted — several tests
  were rewritten after review because they asserted the wrong thing. Two examples
  worth naming, because they are the kind of thing a reviewer should look for:
  - a test asserted `additionalProperties: false` returns 400. It does not: Fastify's
    Ajv strips unknown properties instead. The test was replaced with one that pins
    the behaviour that actually protects us — the client cannot choose its own user id.
  - a test asserted a token signed with a different secret is rejected, but built the
    "different" instance with the *same* secret, so it could not fail. It was replaced
    with a hand-forged HMAC and an `alg: none` token.
- **Code review.** Whole-repository audits against the subject, which is how most of
  the defects listed in the git history were found — the px/dp bug in the viewer's
  hit testing, the check-then-insert race in `createUser`, the portrait camera framing.
- **Documentation.** Drafted with AI, checked against the code. Every factual claim
  in `API.md` and the READMEs was re-verified against the source, because stale
  documentation was a recurring problem.

## Where it was not

- **Architecture.** Splitting the ligand pipeline into the app and leaving the
  backend auth-only was our decision, argued in [`fieldtrip.md`](fieldtrip.md). It
  cost us a working backend API we had already built.
- **The 3D renderer's design.** Grouping `InstancedMesh` per element and per bond
  colour — rather than one mesh with a per-instance colour attribute — was chosen
  because it keeps same-element highlighting a single material write instead of a
  custom shader. That trade-off is ours and we can defend it.
- **Anything we could not check.** The instancing rewrite, the half-bond geometry
  and the `instanceId → atom index` mapping were traced by hand against the
  pre-rewrite formulas before being trusted, and the math that makes them correct
  was moved into `frontend/src/lib/moleculeGeometry.ts` specifically so it could be
  unit-tested rather than argued from a diff.

## The honest caveat

AI is confident about things it cannot observe. It cannot tell us whether the
renderer is fast on a real GPU, whether the share snapshot comes out the right way
up, or whether TalkBack reads the viewer sensibly. Those are settled by installing
the APK and walking the app, which is the last step before hand-in and the only
evidence here that is not reasoned from source. Nothing in this repository is
described as verified on hardware unless it was.
